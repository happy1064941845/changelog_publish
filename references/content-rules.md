# 更新日志内容规则

供生成 `items` 定稿清单时参考。规则的目的是让写进页面的文案像人写的、分类不串、格式统一。

## 一、清单格式

每行一条，竖线分隔四段：

```
类别 | 模块 | 标题 | 描述
```

> **这是硬要求，不是建议。** 传给写入脚本的 `items` 必须是这套四段式清单；**绝不能把用户的
> 更新说明原文整段塞进 `items`**。脚本内置格式闸，遇到"整段没有竖线"或"部分行缺竖线"会直接拒写。
>
> 为什么这么严：一旦原文漏过去，缺竖线的行会被兜底成"新特性 + 无模块 + 无描述"，页面症状是
> **所有条目都挤在【新特性】、标题拖着句号、没有模块蓝胶囊、没有描述行**——很难一眼看出来。

- **类别**：只写 `新特性` / `特性更新` / `Bug 修复`（也认英文别名 `features` / `updates` / `fixes`、`Feature Update` / `Bug Fixes` 等）。
- **模块**：产品模块名，会渲染成蓝色胶囊标签（如 `环境管理`、`前端`、`AI SHELL`）。可留空。
- **标题**：一句话结论，**提炼后的**，不是把用户原话剪短。
- **描述**：补充说明，**不允许留空**（用户没写时由模型生成，见「二之三」）。用反引号包命令/文件名会渲染成行内代码，如 `` `job-env-manager` ``。

## 二、分组归属（最容易错）

**用户输入自带分组标记时，一律以用户标的为准，不得自行重判。**

| 用户写的 | 归到 |
|---|---|
| `New Features` / `新特性` / `Features` / `新增` | **新特性** |
| `Feature Update` / `特性更新` / `Updates` / `优化` / `调整` / `改进` | **特性更新** |
| `Bug Fixes` / `修复` / `Fixed` / `修复问题` | **Bug 修复** |

**最大的坑**：`Feature Update` 名字里带 "Feature"，极易被误升格成【新特性】。它应归**特性更新**——那是"已有能力的更新/发布"。只有**全新功能、全新入口**才归【新特性】。

实测反例：同一份 v1.7.0 内容，人工归【特性更新】3 条；AI 误判成【新特性】2 条 +【特性更新】1 条。

## 三、文字风格（要改写润色，不是照抄）

任务是**润色**，不是搬运。**用户原文只是素材，每条记录的成品（模块 + 标题概括 — 描述说明）都必须由模型提炼改写产生。**

### ★ 防照抄闸门（先于一切风格规则）

逐条自检：**把写好的标题拿回用户原文里搜，能整句找到（或仅差个别字、标点）= 照抄，必须重写。**

照抄的典型症状：

| 症状 | 说明 |
|---|---|
| 标题 = 用户原句剪短版 | 只删了字，没提炼结论 |
| 标题 / 描述一字不差 | 模型没介入，纯搬运 |
| 描述 = 用户原句的"剩余部分"原样粘贴 | 拆了段但没改写 |

正确动作三步：**① 判断模块 → ② 提炼结论性标题概括 → ③ 其余信息改写成书面语描述**。改写时允许调整语序、合并信息、换措辞，只要不编造用户没提的功能点。

### 口语 → 书面语

| 用户原话 | 应写成 |
|---|---|
| 点一下…就能…啦 | 点击…即可 |
| 做好的 | 完成的 |
| 和使用 | 使用 |
| 现在支持了 | 支持 |
| 弄好了、搞定了 | 完成 / 已修复 |

### 标题要提炼结论，不是剪短原话

| | 写法 |
|---|---|
| 反例（照抄） | 修复移动端环境种类和状态筛选的问题 |
| 正例（提炼） | 修复移动端筛选标签高亮残留的问题 |

反例只是把用户原话抄了一遍；正例说出了**现象结论**（什么问题、什么表现）。

### ★ 一条必须拆成"标题 + 描述"两段，不能整句塞进标题

这是最容易出现的偏差：用户发来的是一长句，模型**原样整句**塞进 `title`、`desc` 留空
→ 页面上就是一大坨没有重点的长句（模块胶囊还在，但看不出改了什么）。

**拆段三步**：

1. 先挑出**最核心的结论**（改的是什么 / 修掉的是什么现象）→ 写进 `title`。
2. 剩下的补充信息（怎么生效、影响范围、依赖什么）→ 挪进 `desc`。
3. **`desc` 一律不为空**：原句有细节就搬进 `desc`；原句只有个结论、没别的信息
   → 按下面「二之三」**替用户补一条合适的描述**，**不许填空字符串**。

**自查标准**：

- `title` ≤30 字、**不含逗号**、结尾不加句号；
- **`desc` 必须非空**（空字符串一律视为没做对）；
- **`title` 里出现逗号 = 没拆干净**——逗号往往就是拆分线，逗号前是结论、逗号后是细节。

| | 示例 |
|---|---|
| ✗ 整句塞 title | `title`="job-env-manager 更新至 0.0.66，提升服务稳定性，优化作业环境卡片偶现无法加载的问题"，`desc`="" |
| ✗ desc 留空 | `title`="支持 .drawio 画图文件在线预览"，`desc`="" |
| ✓ 拆成两段 | `title`="job-env-manager 更新至 0.0.66"，`desc`="提升服务稳定性，优化作业环境卡片偶现无法加载的问题。" |
| ✓ 补出描述 | `title`="支持 .drawio 画图文件在线预览"，`desc`="无需下载，在资源管理器中即可直接打开并查看画图内容。" |

> `write.js` 的解析是**逐字段对齐**的：`title` 里塞太多，写进页面后 `cl-t` 就会很长、`cl-d` 缺失，
> 视觉上直接失衡。拆段这一步做在内容整理阶段，比事后修补容易得多。
>
> 另：`write.js` 渲染时 **`desc` 为空则不输出描述行**（`cl-d` 整块不生成），
> 页面就只剩一行标题——这正是要避免的观感。

## 二之三、desc 为空时必须补（★ 与"不编内容"不矛盾）

**规则：任何一条的 `desc` 都不允许是空字符串。** 用户只给标题、没写描述时，模型**必须**替他补一条。

补的取材顺序（越靠前越安全）：

1. **展开 `title` 里已有的信息**（首选）——把标题的动作/对象说细。
   - 「支持 .drawio 画图文件在线预览」→「无需下载，在资源管理器中即可直接打开并查看画图内容。」
   - 「修复移动端筛选标签高亮残留的问题」→「取消选中环境种类或状态筛选条件后，对应标签不再残留高亮状态。」
2. **补该类改动的通用影响**（允许）——稳定性 / 性能 / 兼容性 / 易用性方向的常见结果。
   - 「提升服务稳定性」「优化加载速度」「改善使用体验」。
   - 版本升级类：「保持与上游版本对齐」「修复上游已知问题」。
3. **补这类功能的常见使用场景**（允许）——说明它解决什么场景下的什么问题。

**唯一红线：不许编用户没提的"功能点 / 数据"。**

| | 判断 |
|---|---|
| ✓ 允许 | 用户说「支持 .drawio 在线预览」→ 描述「无需下载，在资源管理器中即可直接打开并查看。」（在展开已说的事） |
| ✗ 违规 | 同一条 → 描述「同时支持导出为 PDF 与 PNG。」（"导出"是用户完全没提的新功能） |
| ✗ 违规 | 描述里加「加载速度提升 50%」这类用户没给的数字 |

**一句话记住**：**描述可以是你写的，功能必须是用户说的。**

**用户写了但过于简略的描述，也一并优化**（如只有「优化体验」四个字 → 按上面三条补全）。

### 其他

- 去冗余："（依赖：运行中的 X）" → "（依赖运行中的 X）"
- **中英文/数字相邻处保留一个半角空格**（与提示词 A 规则 8 一致，**别删**）：
  正例 `优化 Draw.io 与 AI Shell 交互体验`、`修复 CodeArts 连接代理服务失败问题`、`升级至 v1.0.13`；
  反例 ✗ `优化Draw.io与AI Shell交互体验`、✗ `修复CodeArts连接代理服务失败问题`（英文单词和中文粘在一起）。
  已用反引号包起来的代码（如 `` `job-env-manager` ``）**内部原样保留**，不要动它内部的空格。
- 保持克制：**改写措辞、提炼标题、按需补描述**是必须做的；**编造用户没提的功能点**是违规的。两者只差一步，别混。

## 四、常态约定

- **页码版本行只写日期**，不带时分（`2026-10-20 · v1.7.0`，不是 `2026-10-20 17:15 · v1.7.0`）。脚本已自动截取。
- **一个版本号一次发布**。已存在的版本号会被幂等检查挡下；真要改，加 `"overwrite": true` 整块覆盖（见 `rollback-and-troubleshooting.md` 第二节）。
- **版本号原样保留**，可带后缀（`v1.6.3`、`v0.0.1-alpha.29`），不要改写。
- **不编功能点，但要补描述**。用户没说的**功能、能力、入口、数据**不要补；但**描述（`desc`）必须补非空**——见「二之三」。一句话：描述可以是你写的，功能必须是用户说的。
- **末段别拖句号**：标题是结论短语，结尾不加 `。`；描述可以带句号。（页面用 `::after` 自动补 `—` 连接符，标题带句号会显得很怪。）

## 四之二、预览版式（★ 硬格式，由 `scripts/lib.js` 产出，禁止手写）

预览**不是模型自由发挥的文本**，而是脚本按固定版式渲染出来的。要出预览就跑
`write.js` 并带 `preview_only: true`，把返回的 `preview` 字段**原样**贴给用户。
版式（与 Coze 工作流 A 节点三逐字一致，逐字符都不能改）：

```
📋 更新日志预览
（空行）
版本  v1.8.0          ← 「版本」后是两个半角空格
日期  2026-10-23 14:30  ← 同上，「日期」后两个半角空格；预览头部可带时分
条数  2 条            ← 同上
（空行）
【特性更新】1 条
· 环境管理  自定义环境支持打包发布    ← 圆点 + 空格；模块与标题之间两个半角空格
   —— 完成的…                       ← 描述行前缀：3 个半角空格 + —— + 一个空格
（空行，分类之间）
【Bug 修复】1 条
· 前端  修复置顶偶发报错
（空行）
────────────              ← 12 个 U+2500
确认无误，回复：确认
要改内容，把修改后的说明重发一遍，我重新出预览。
```

要点：

- 只有**非空分类**出块，分类顺序固定 **新特性 → 特性更新 → Bug 修复**。
- **描述为空的条目不输出 `—— ` 行**（脚本行为，别为此去补空描述）。**正常路径下不该出现"描述为空"**——按「二之三」，内容整理阶段就必须把 `desc` 补成非空。
- 头部「三行头」的**双空格对齐**是刻意的，别改成单空格或全角空格。
- 改了内容 → **重新跑脚本出预览**，不要手动编辑预览文本（手改就与 Coze 不一致了）。

## 四之三、提交规则与页面块样式（★ 与 Coze 写入节点完全一致）

写进页面的块样式，以及写入侧的提交规则，都与 Coze 工作流 B 节点三**逐字一致**，
由 `scripts/lib.js` 承载（唯一定义源）。要点（**别各自发明**）：

- **页面块**：`cl-ver` / `cl-month-date` / `cl-cat` / `cl-cat-h` / `cl-list` / `li` /
  `cl-tag` / `cl-t` / `cl-d` 的标签、层级、缩进、空行**逐字符一致**；`—` 分隔符由 CSS
  `.cl-t::after` 生成，**不要手写**。
- **格式闸**：`items` 每行必须 `类别|模块|标题|描述` 四段（用竖线）。整段无竖线或部分行缺竖线 → 拒写。
- **条数闸**：带了 `count` 且与 `items` 实际解析条数对不上 → 拒写（防"确认了 N 条、只写了 N-1 条"）。
- **幂等拦截**：页面已有同名 `data-version="vX"` 时默认拒写，并给出三条出路；`overwrite=true` 则
  **整块替换**同名 `cl-ver` 块，**位置与版本号不变**。
- **三种插入位置**：`same-month`（并入当月，插到 `</h3>` 之后）/ `new-month`（新建月份分组，
  放在锚点之后并同步补 `.cl-rail` 一行）/ `overwrite`（覆盖同名版本）。
- **回执文案**：`并入 Y年M月` / `覆盖原 vX（位置不变）` / **`新建 Y年M月分组`**；
  成功行首 `已写入 vX` / `已修改 vX`；commit message `docs(changelog): vX` / `docs(changelog): 修改 vX`。
- **`view_url`**：默认指向文档站更新日志锚点，末尾无 `#` 时自动补 `#changelog`。

改这些规则**必须三处同步改**（`lib.js` + Coze 预览/写入节点），再跑 `scripts/parity-test.js` 回归。

## 五、分类上限与排序

页面按固定顺序渲染：**新特性 → 特性更新 → Bug 修复**，只有非空分类会出块。同分类内按给定顺序排列。

- **每类最多 8 条**（与 Coze 预览节点一致，超出会被脚本丢弃）。同一件事只写一条，不要拆成多条。
- **占位行会被过滤**：`无` / `暂无` / `无变更` / `n/a` 等整行会被丢掉，不要靠它凑数。
- **长标题会被兜底拆段**：`title` 超过 26 字且含 `，,：:—` 时，脚本在第一个分隔符处自动切开
  （前半进 `title`、后半进 `desc`）。这是兜底，**不是让你偷懒**——正常应在整理阶段就拆好。

## 六、页面结构参考

写入依赖页面已有的这套 class（文档站 `AIDevspace.html` 里已定义）：

| class | 作用 |
|---|---|
| `.cl-month` / `data-month="2026-10"` | 月份分组容器 |
| `.cl-month-h` | 月份标题（如「2026年10月」） |
| `.cl-ver` / `data-version="v1.7.0"` | 单个版本块（幂等检查靠它） |
| `.cl-month-date` | 版本行：`2026-10-20 · v1.7.0` |
| `.cl-cat` / `.cl-cat-h` | 分类块 / 分类标题 |
| `.cl-list` / `li` | 条目列表（圆点由 `li::before` 生成） |
| `.cl-tag` | 模块蓝色胶囊 |
| `.cl-t` | 标题（粗体；`—` 分隔符由 `::after` 自动生成，**不要手写**） |
| `.cl-d` | 描述 |
| `<!-- CHANGELOG:START -->` | 插入锚点（新月份插在它之后） |
| `.cl-rail` | 右侧月份导航（新建月份时同步补一行） |

### 条目的三段结构与各自样式

每条 = **模块 + 标题 + 描述详述**，三段各进一个标签、各有自己的样式：

| 段 | 进哪个标签 | 页面样式 | 可空 |
|---|---|---|---|
| **模块** | `cl-tag` | 蓝色圆角胶囊，12px，浅蓝底 `#eaf3ff` ＋ 蓝字 `#2e7cf5` | 可（留空则不出胶囊） |
| **标题** | `cl-t` | 14px **加粗**、深色 | 不可 |
| **描述详述** | `cl-d` | 14px 常规字重、次级灰 | 可 |

对应到定稿清单，就是 `类别|模块|标题|描述` 里的后三段。三者都是内联块，
**挨着渲染成一行**：`[胶囊] 标题 — 描述`，中间那个 `—` 由 `.cl-t::after` 自动补，**不要手写**。

> **漏掉模块的后果**：条目没有 `cl-tag` → 页面上少了蓝色胶囊，一条条长得都一样、扫不出重点。
> 模块名要**具体到 2-6 个字**（`环境管理`／`前端`／`连接器`／`hwcloud CLI`），别写「系统」「功能」这类空泛词。
